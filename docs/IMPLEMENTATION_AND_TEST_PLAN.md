### Completed implementation order

1. Inspected existing tenant JSON backups, hosted worker, export/settings UI, session validation and deployment constraints; retained report/export contracts and earlier barcode work.
2. Added platform-wide settings/jobs/append-only recovery events, unique schedule keys, settings validation and a reversible additive migration.
3. Implemented private-storage checks, native consistent snapshots/dumps, authenticated encryption, integrity verification, atomic publication and checked secondary copies.
4. Extended the existing worker with durable scheduling/queue execution, nonpooled explicitly released PostgreSQL locks, bounded retries, leases/interruption handling and independent retention. Native failure does not stop legacy export execution. The final storage-health/share-delete adjustment was followed by a successful 30-case backup-service test run and the real PostgreSQL suite.
5. Added explicit platform operator/recovery policies and API controls; integrated the responsive existing BackupPage, preserved ordinary-role business exports and clarified export labels.
6. Added confirmed isolated recovery CLI, encrypted recovery events independent of the source DB, deployment instructions and recovery drill; tested actual encrypted native round-trip and module regressions.

### Remaining deployment order and limitations

1. Review/apply the metadata migration through the existing approved deployment process, preserving a predeployment infrastructure recovery point. This audit did not perform that action on production.
2. Provision trusted PostgreSQL tools, compatible release/extension/role dependencies, private persistent volume, independent encrypted secondary storage and separate secret/key recovery. Configure platform operator and recovery allowlists. No production credentials were supplied or stored in source.
3. Create a manual archive and qualify its secondary copy and representative isolated application recovery, including Data Protection, logos, ML assets and session/credential reconciliation. DPAPI-protected key rings may require original Windows user/machine cryptographic material; copying a directory to a new host alone is insufficient without a rehearsed key-recovery method.
4. Measure real dataset disk headroom and restore/validation time; approve RPO/RTO and offsite failure-domain/transport protection. Local secondary-file copying was tested, no remote provider, Linux ACLs or physical backup media was tested.
5. Enable daily/monthly schedules and monitor history/health, failed/interrupted jobs and disk use. Default offsite-before-prune policy can intentionally retain more files than the UI retention count when secondary copies are not verified.
6. Perform any live cutover only through the [administrator-guided recovery procedure](RECOVERY_DRILL.md). Live overwrite remains unavailable. Reconcile running job snapshots and avoid exposing restored sessions/integrations prematurely.

Retained archive/history browsing currently shows the latest 100 jobs; administrative CLI recovery remains possible from trusted protected older files and the independent inventory. Crash orphans and encrypted operator event retention require deliberate operator management. No production recovery certification is claimed.

## Release and safety gates

- Audit/documents first (completed in this change), then implementation in small packages with explicit tests.
- No automatic migration/backfill of existing barcode values or identifiers. Inspect approved staging data for collisions before proposing any schema change. No production migrations during audit.
- A barcode association requires unchanged balances, StockMovements, purchases and provenance; its own safe security audit is expected.
- A recovery release requires complete classified coverage, protected assets/keys, an isolated successful restore and an operator rollback plan. Keep 501 until that gate is met; a passing dry-run must not imply data is restorable.
- A report release requires authorized source-data content, accurate units/precision and all-page review. A responsive UI release requires the entire route/state/role matrix, not only existing short-data smoke.
- Reuse authorized existing services/components; do not duplicate working exports, add native shell assumptions, remove tenant keys, relax authentication or rewrite historical transactions.

Remaining BLOCKED verification is specific: no configured disposable DB for the integration run; no approved representative recovery copy/production topology/RPO/RTO/key ownership; no physical scanner/printer/device qualification. These do not block the source repairs or design work above. They block claims of PostgreSQL/recovery/device production readiness.
