The all-pages readability follow-up is recorded in [ALL_PAGES_RESPONSIVE_AUDIT.md](ALL_PAGES_RESPONSIVE_AUDIT.md) and [ALL_PAGES_RESPONSIVE_FIX_REPORT.md](ALL_PAGES_RESPONSIVE_FIX_REPORT.md). ## Scope and evidence

Read `frontend/src/router/index.tsx`, `docs/FRONTEND_ROUTE_MAP.md`, the earlier responsive audit, shared shell/mobile navigation/UI/theme/auth/query keys/API clients, and all registered page components. Reviewed subordinate barcode, variant, supplier mapping/history, purchase assistant/invoice/voice/payment/damage/delivery, report/export, historical consumption/forecast, backup/recovery, permission and credential workflows. Production pages continue to consume existing scoped APIs; example records live only in test fixtures. No backend policy, tenant selector, inventory calculation, migration or database was changed for this frontend task.

Route evidence is `frontend/e2e/responsive-routes.spec.ts`: 40 samples including the index, redirect aliases, dynamic detail/edit/activity paths, public authentication and wildcard. Each is checked at 360×800, 390×844, 768×1024, 1366×768 and 1920×1080 in light and dark themes. Tests verify visible content, document **and main-content** overflow, uncaught page errors and the route error boundary. Measurements also record unnamed visible form controls. Geometry alone is not a complete functional or accessibility certification.

## Dialog and nested workflow checklist

`ui-audit-workflows.spec.ts` also checks representative text contrast in both themes and explicit keyboard permission deltas. It checks geometry, initial focus, contained Tab/Shift+Tab, Escape and focus return at **all five requested viewports** for category create/edit/delete; type create; supplier create/edit/delete, mappings and history; broker create/edit/delete; user create/edit, permissions and login credentials. It also checks the user form at 360×400 to simulate a smaller keyboard viewport, theme persistence, network recovery for search/reports/notifications, and Admin defaults.

Shared `DialogFrame` uses a native modal dialog to isolate background content. `Modal` and `ConfirmDialog` reuse it. Variant delete, catalog archive and version-conflict dialogs inherit the same behavior; unit/barcode/variant suites exercise their requests. Type edit/delete use the same modal and confirmation as type create/category actions. Catalog/purchase creation and stock count/adjust/reconcile are inline workflows, not missing routes. Damage reporting is inline, with labeled fields, validation, pending guards and role checks. Existing purchase delete, settings discard, checklist removal, backup deletion and delivery confirmations use browser confirmation dialogs; this task does not silently approve or bypass them.

The mobile More drawer retains its navigation groups, safe-area layout, focus trap, Escape and business switching. Background main/header/bottom navigation are inert while it is open. Notification preview remains a non-modal region with outside/Escape dismissal and visible read failure. Global search is a named modal with a combobox/listbox, keyboard movement and contact details. Barcode printing retains its dedicated print sheet; reprinting does not issue a stock operation.

## Unverified limits and deployment checks

Overall complete production UI qualification is **PARTIAL**. No page is deliberately left blank or populated with invented business metrics. All registered route samples are exercised, but their full role/data/network/state cross-product is not exhaustively tested. Browser API fixtures prove client behavior and request contracts, not live backend/database interoperability, production latency, every historical record, tenant enforcement or real permission deployment. Existing server isolation and test suites were retained.

Physical camera/USB scanner/printer, actual Android/iOS virtual keyboards/safe areas, screen readers, Safari/Firefox and high-volume/long-table performance on a production tenant were not tested. AI provider/model availability, WhatsApp delivery, real backup storage/recovery and unattended downloads still depend on deployment configuration and hardware; they remain explicit unavailable/error states. No production restore, migration, stock write or external message was performed during verification. No standalone role-management route exists; roles/permissions are managed within Users. Item-specific purchase history has no dedicated API in this scope; broker fields beyond the actual DTO are not invented.

Before deployment, test representative tenant data and role overrides against a disposable backend, qualify supported browsers/devices/scanners/printers, and review additional production-data states beyond the saved fixture screenshots. These are concrete verification limits, not claims that the entire UI is perfect.
