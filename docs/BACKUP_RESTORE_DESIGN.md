### Archive contract and integrity

Published filename is `<job UUID without hyphens>.wab`, never an API-supplied path. `WABK0001` envelope contains a non-secret key ID and random 16-byte file salt. HMAC-SHA256 derives a per-file AES-256 key from a random 32-byte master key. Independently authenticated AES-GCM chunks are at most 1 MiB; their header, sequence and length are authenticated, including an empty terminal record. Wrong keys, truncation, reordering, appended bytes or modified ciphertext fail validation. SHA-256 additionally identifies the exact published encrypted file.

Inside the authenticated envelope are exactly `manifest.json` and a PostgreSQL custom `database.dump`. Manifest version 1 records archive UUID, UTC creation time, hashed source identity, PostgreSQL server version, ordered migration IDs, public table row counts and dump digest. It contains no passwords, tokens, connection strings or encryption keys. Native database contents remain sensitive and encrypted. Exact-entry processing extracts no user-selected paths. Normal verify/restore requires exact migration-history compatibility with the running tool; `inspect` reports migration IDs to select a matching application release for an older archive.

A native database dump contains schema, records, indexes, constraints, tenant IDs and migration history; cluster roles/tablespaces and filesystem assets are separate dependencies. The mechanism follows the [PostgreSQL 17 pg_dump contract](https://www.postgresql.org/docs/17/app-pgdump.html) and uses [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html). Restoring SQL executes code from its source; accept only archives from trusted protected storage and keep the rehearsal isolated from production integrations.

### Jobs, restart and failure handling

A dedicated nonpooled PostgreSQL session advisory lock, explicitly unlocked on disposal, serializes workers; a separate advisory lock serializes job/settings changes. A 90-minute execution lease protects crash recovery if the lock connection is lost. Whole-job execution cancels after 75 minutes; each native process after 40 minutes. Cancellation kills and awaits the child before recording interruption. Hard-crash child processes cannot publish an archive; an abandoned plaintext workspace may need private operator cleanup. Expired running leases become interrupted. Scheduled jobs retry the same record up to three total attempts, with 10/20/30-minute backoff; manual failures are visible and require a new operator request.

Catch-up is bounded to the current local date and month, rather than manufacturing missed historical backups. Disabling a schedule cancels its pending/failed/interrupted runs; already-running jobs finish safely. A failed native worker does not suppress the existing business export worker branch.

Temporary plaintext is restricted to an owned private workspace and removed after normal completion/failure. Publication never overwrites an existing UUID artifact. A crash after publication but before job status commit can leave a valid orphan; automatic retry fails safely rather than replacing it. Inspect/reconcile such a file with the CLI and retained checksum before updating any operational record. Do not remove current workspaces; after stopping workers and native processes, a privileged operator may remove confirmed abandoned directories. No automatic arbitrary recursive cleanup is exposed.

## Three separate contracts

1. **Operational export**: existing CSV/XLSX/PDF/ZIP/subset JSON. User download, redacted per role, filtered range, explicit omissions. It supports analysis, not recovery. Browser auto-download is once when app opens, not unattended server disaster recovery.
2. **Tenant recovery archive (proposed v2)**: complete business-owned state with canonical identifiers and dependencies; separately versioned manifest; no universal account/session secrets. First restore into an isolated staging database with existing tenant identity. No automatic merge into an occupied Business.
3. **Operator disaster recovery**: full PostgreSQL database plus separately protected external assets/key material/configuration inventory, validated on a new target. Includes global accounts and protected credentials under operator security. Existing pg_dump rehearsal is the foundation.

## Proposed archive and job design

- Manifest: format/version, backup UUID, source BusinessId or operator scope, snapshot start/end, application release, migration IDs, PostgreSQL version, covered tables/columns, row counts, file SHA-256, exact omissions/dependencies, asset checksums and verification status. Authenticate the manifest/artifact with signature or authenticated encryption; checksum alone is not provenance.
- Tenant data: preserve UUIDs, exact decimal values, nulls, UTC timestamps/enums and relationship keys, with deterministic row order. Never export `xmin` as restorable identity; fresh target assigns concurrency versions, then clients reload.
- Storage: write restricted temporary artifact, validate, flush/publish atomically; record immutable job outcome and checksum; protected offsite copy verified before expiring required prior backups. Do not expose absolute server paths to UI. Quotas apply to bytes, rows, duration and concurrent jobs.
- Schedule: use existing service/worker with durable run tracking and tenant/date job claim, not a new architecture. Catch up once after downtime; bound retries with failure/freshness notifications. Define operator-owned retention/RPO/RTO before deployment. Proposed starting policy for discussion: daily full logical recovery copy, several daily/weekly protected copies and scheduled monthly recovery verification; these are not currently configured guarantees.

## Safe restore sequence and rollback

1. Authorize operation, identify exact archive/provenance and explicit new target. Reject current source/live connection, unknown archive version and nonempty/unapproved target. Avoid accepting arbitrary host/path/SQL from HTTP requests.
2. Validate manifest authentication, file checksums/limits, schema/migration compatibility, identities, tenant scope and every FK/unique key. Report exact unsupported/missing state; write nothing in live app.
3. Provision a clean isolated target using approved operator tooling. Restore trusted full dump or complete validated tenant archive there. Keep mail/WhatsApp/backup/other workers and outbound integrations disabled, so restored jobs do not send or mutate externally.
4. For a tenant archive, insert in dependency order using a dedicated staging path that preserves historical rows without ordinary mutation hooks: identities resolved → business/master data → orders → lines/relationships → ledgers/provenance → operations/history. Respect constraints; do not casually disable query filters or bypass tenant FKs. Full dump restore uses PostgreSQL's ordered archive. No domain purchase replay or stock adjustment to reconstruct balances.
5. Verify row counts plus deterministic key/value digests, FK/check/index presence, all BusinessIds, original immutable facts, current stock and full ledger reconciliation, purchases/lines/payment totals, assets and restricted key decryption. Investigate unexplained differences; never patch missing values with synthetic facts.
6. Verify release/migration state and targeted read-only application smoke. Rehearsal mutation tests use disposable fixture records only. Invalidate restored refresh/reset sessions before any eventual promotion; record recovery evidence in a new separate audit record.
7. Promotion requires a separately approved operational window after representative rehearsal. Retain original source/archive and previous deployment. If validation fails, do not cut over; retain/discard only the isolated target under operator policy. After cutover, rollback routing only with an explicit policy for new writes; stale restored data must not overwrite later transactions.
