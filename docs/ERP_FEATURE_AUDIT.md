## Evidence and classification rules

- **VERIFIED COMPLETE**: the narrowly stated behavior exists and relevant checks executed in this audit support it. This is not deployment certification.
- **PARTIAL**: useful implementation exists, but required coverage, behavior, or verification is incomplete.
- **BROKEN**: source or executed checks demonstrate an incorrect contract or behavior. Static findings explicitly identify their trigger; they need regression tests.
- **MISSING**: no implementation found in the inspected routes, services, schema, dependencies, scripts, and repository search.
- **BLOCKED**: verification or activation requires unavailable infrastructure, a recovery target, or a settled security contract. An intentionally disabled endpoint is not a working restore.

Earlier readiness documents are historical evidence, not fresh test results. See [IMPLEMENTATION_AND_TEST_PLAN.md](IMPLEMENTATION_AND_TEST_PLAN.md) for commands, results, limitations, and acceptance gates. Every finding below has a detailed design entry in the linked document, including dependencies, security implications, and required tests.

## Persistence and security assessment

`AppDbContext.CurrentBusinessId` comes from selected authenticated claims through `CurrentUserService`; absent context becomes Guid.Empty. Global filters plus many composite `(BusinessId, Id)` foreign keys enforce tenant-shaped reads and relationships. The session validator checks current User, refresh-token family, active Business and Membership, and replaces role/permission claims from current membership. These controls must be reused, including for SuperAdmin operating within a selected Business.

Catalog stock balances are numeric columns (`CurrentStock`, `PhysicalStock`, `ReservedStock`, precision 18,4) with Guid concurrency token. `StockService` records delta/before/after and actor; `PurchaseService` uses the stock service within a receipt transaction. Purchases use PostgreSQL `xmin` as `Version` (model snapshot). Restores cannot preserve `xmin` as a stable business identifier: require clients to reload and issue fresh versions. Barcode edits in `CatalogService.UpdateAsync` currently do **not** assign balance fields despite their presence in the submitted DTO; this invariant must be retained and explicitly tested.

`AppDbContext.ProtectStockLedger` disallows EF tracked updates/deletes of stock movements, audit/prediction/integration history and historical import provenance. `PrepareMutationRecordsAsync` allowlists audited fields including Barcode, excluding credentials. These are application-level protections: `ReferenceStockLedgerProtection` changes FK delete behavior, not a PostgreSQL immutability trigger; raw SQL or a privileged restore operator can bypass them. Do not claim database-level immutable audit enforcement. Recovery must preserve historical rows and validate hashes/relationships without replaying ordinary domain mutation hooks.

App specifications are not a production schema inspection. No live credentials were read, no production migrations/restores were run, and no production connectivity or tenant-isolation certification is claimed. Comprehensive recovery and physical scanner/browser qualification remain explicit release gates.

## Implementation direction

Order: settle contracts/security inconsistencies → barcode identity and narrow update → truthful export labels and guarded client → complete recovery coverage and storage → isolated restore validation/rehearsal → PDF layout foundation and separate reports → shared UI/state/navigation repairs → route-wide regression and recovery qualification. Shared UI repairs can proceed alongside recovery design once audit artifacts are reviewed; they need no architectural rewrite.
